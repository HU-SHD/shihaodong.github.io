失败反思：Agent本地部署与Deepseek V4 Free API接入的尝试，从反向代理到本地Ollama模型等四种方案无效的技术架构反思

从“白嫖 API”到本地 Agent 瘫痪：一次 OpenScience 白嫖的尝试带来的架构反思

最初，我其实只是想在本地部署的 OpenScience 里免费接入 DeepSeek V4 Flash。今年6月之前，openScience事实上是支持免费的deepseek-v4模型的部署。但今年6月之后openScience进行了更新，OpenCode Zen不再支持deepseek模型的免费接入。6月到9月由于需求并不迫切，我并没有考虑对本地的openScience在10月初我再次用到openScience，折腾了一周多，花费了很大精力还是失败了，没有找到免费的无限制ds-v4模型调用的方式……果然，想吃大肥鱼的白饭还是太困难了…总而言之，这篇博客负责记录我对于“免费调用无限制ds-v4模型”这个设想的所有尝试和失败的结果，站在另一个角度回顾和反思我的尝试和想法。

我尝试了各种方案：反向代理的伪兼容、浏览器抓包，本地 Ollama 部署，中转站模型的调用……开源生态在广度上近乎没有任何缺点和不足，几乎所有需要的技术、平台、功能实现都可以在开源社区中找到，这得益于几十年计算机开源社区上所有作者的共同努力。我对开源社区的印象一直都是“近乎万能”。我知道它部分功能肯定不如一些付费软件付费平台效果好，但我依旧相信能够有简单易上手的平替项目存在。这次尝试让我意识到“开源≠万能“，开源无法替代付费。

这篇博客将讲述我使用openScience尝试白嫖deepseek-v4的完整过程和尝试，并讲述我的看法和观点，希望这篇博客能对你有所帮助。

一、 对于白嫖的各种尝试

1. OpenRouter平台ds-v4 flash的消失

最初我把目光投向 OpenRouter，试图寻找带 :free 后缀的 DeepSeek V4 Flash，想要使用免费额度从OpenRouter上调用API。理论上成立，但实际查找发现官方根本没有提供这个版本，在搜索“Deepseek V4 Flash”关键词时并没有只有带 :free 后缀的模型。随后又尝试了搜索“Deepseek Free”关键词，只有 deepseek-r1:free 等少数几个速率受限的模型。免费额度有限，模型速率受限，于是该方案被我舍弃。

失败后我开始搜寻OpenScience内置免费模型的原理，随后通过大肥鱼，我知道了 OpenScience 内置模型是通过 OpenCode Zen 免费池提供API。检查OpenScience的API，base，update后发现在老旧的 v0.3.0 版本无法找到并成功接入OpenCode Zen，OpenScience官方文档和OpenScience Desktop的官方文档中均指出在v0.6.x版本才能够正确接入当前版本的OpenCode Zen。

要在保存本地对话数据的前提下进行更新事实上并不困难，前提是你直接使用OpenScience Desktop官网提供的exe文件更新。但很不幸的是我选择的是先更新OpenScience……出了点问题但问题不大，使用npm安装时会出现一些报错，例如npm 的 allow-scripts 拦截、uvicorn、fastapi、dotenv 缺失的报错……一路修修补补……。因此建议直接使用OpenScience Desktop开源项目官网提供的v0.6.0的exe安装包，它会同步更新你的OpenScience版本，无需面对npm安装可能遇到的拦截和报错。

最戏剧性的是：当我终于把环境配通，升级完客户端后，OpenCode Zen 里的 deepseek-v4-flash-free 已经被标记为 deprecated……心态有点小崩。

2. 反向代理

心态崩归崩，白嫖的尝试还是得继续的。既然官方渠道走不通，我便开始考虑社区中是否有人也有同样的想法和已经验证成功的方案。于是找到了社区项目 deepseek-web2api-free。这个项目的逻辑很清晰：把网页版 DeepSeek 的私有接口，转换成 OpenAI 兼容的 API。

该方案的实现步骤不难：

  • 使用git clone https://github.com/snake-aabb-wtf/deepseek-web2api-free.git，然后进入项目目录 deepseek-web2api-free 通过 requirements.txt 安装依赖。
  • 在浏览器中登录 DeepSeek 网页版，打开开发者工具，切换到 Network（网络） 标签，随意发送一条消息。在请求列表中找到 chat/completion 请求，从请求头中复制 Authorization 字段和 Cookie 字段的完整值。
  • 运行 python start_server.py。默认情况下，服务会在 http://localhost:8000 启动，可以通过修改配置文件更改启动地址。随后在配置文件配置账号密码，密码默认是 admin 。当然也可以修改配置文件直接配置 Token 和 Cookie ，或配置完毕本地账号密码登录后的 WebUI 账号池列表中添加 Token 和 Cookie。

配置完成后进行验证，终端将返回类似{"object":"list","data":[...]} 的 json 数据。

在此之后正常配置好OpenScience的自定义端点， UI 界面中成功显示了 "deepseek-chat" 模型，并且OpenScience 对话框也成功返回了 deepseek-chat 的回复。

3. 对话通了，本地死了

然而，这种喜悦只持续了一分钟不到。在对话成功返回了模型回复时，我便开始直接尝试让 deepseek-chat 读取我过往工作区的对话，进而衔接上之前的工作进行后续的CRUD。当我输入对话需求，要求模型读取过往工作区时， Deepseek 的确开始了思考，然而思考的内容就像条件为 1 的for循环，永远停留在build的前一段命令。等待了几分钟重复的深度思考，我人为终止了进程。在 WebUI 界面中，http://localhost:8000 地址的服务始终正常，并且显示“总请求次数：16 成功：15 失败：1”。检查了UI界面的配置，确认参数、配置、日志没有问题后我尝试向大肥鱼询问。随后打开了Deepseek网页版的界面，发现对话记录中出现了16条甚至更多段对话，并且每一条对话的内容如出一辙，左侧缩略栏的标题也几乎一样。

很遗憾，虽然反向代理成功了，但实际上 deepseek-chat 无法实现agent的核心工作——执行build操作，并且也无法实现数据本地保存，对话的信息会被上传到 Deepseek 网页版中导致隐私泄露。这两个严重的缺陷导致该方案被彻底地舍弃。

所以结果显而易见，我们又一次失败了。

4. 本地 Ollama 部署模型

为了找回本地执行能力，我转向本地 Ollama。调用本地 Ollama 部署的模型过程中也出现了一些小问题：例如：端口 11434 被后台僵尸进程占用， context size (4096) exceeded报错等小问题。这些问题并不致命且并不关键，正常部署即可成功将本地模型添加进OpenScience中。该方案被舍弃的核心原因是硬件——本地的显存无法支持3.2万Token的模型上下文。

简而言之，我的锅不够大盛不下这么多的大白饭

我在这里停下了，彻底放弃了继续寻找白嫖API的各种方案，例如使用中转站的API（经典永流传：我们本地部署的GPT（狗头保命））。

二、 技术反思：为什么会处处碰壁？

这次多种失败的尝试暴露出当下 AI 应用生态中几个深层次的架构错位。

1. 对话链路与执行链路的“能力断层”

这是最核心的教训。OpenScience 的底层设计是“模型负责思考，后端负责执行”：

  • 对话链路：前端 → API 端点 → 模型（输出纯文本）。
  • 执行链路：前端 → 本地 Agent Runtime → 解析结构化工具调用（Function Calling / Tool Use） → 调用 bash、读写文件。

deepseek-web2api-free 这类反向代理，只打通了对话链路。网页版 DeepSeek 的接口本身不支持输出结构化的工具调用请求（tool_use 或 function_call）。因此，OpenScience 的本地后端收不到指令，Agent Runtime 就成了摆设，agent就成了残废。

反思：一个不能输出工具调用协议的模型，即便能完美聊天，也无法驱动任何本地 Agent 框架。

2. 反向代理的脆弱与隐性代价

社区维护的反向代理项目依赖抓取网页版 Token 和 Cookie。它们面临三重原罪：

  • 极度不稳定：官方前端改版、增加验证，代理瞬间失效。
  • 凭证过期频繁：Cookie 和 Token 寿命极短，需要反复抓取。
  • 功能残缺：网页版不暴露的能力（如工具调用），代理无法凭空造出来。
  • 隐私与安全风险：你的 Token 和 Cookie 必须明文保存在本地 .env 文件中，一旦项目包含恶意后门，账号隐私将完全泄露。

这些项目适合临时代理、学习协议原理，但绝不能作为生产环境的基建！！！

3. 免费 API 的局限性

从 OpenRouter 的 :free 模型，到 OpenCode Zen 的免费池，我反复经历了“发现 → 配置 → 失效/下架”的循环。大模型推理是有硬成本的，免费的背后往往是限时推广、功能阉割或数据收集。依赖免费 API 构建工作流，无异于在沙子上建高楼。

4. 硬件现实的严酷：本地部署的隐形天花板

用 8GB 显存的 Intel 4060 跑 8B 模型，是我的配置，也是很多人的起手配置。但在实际应用中，上下文长度（Context Window）直接决定了生死。

  • 模型权重（4-bit 量化）约占 5GB 显存。
  • KV Cache（上下文缓存）会随上下文长度线性增长。32K 上下文的 KV Cache 可能额外需要 5-7GB。
  • 两者相加远超 8GB 物理显存。强行拉高上下文只会导致显存溢出（OOM），系统被迫将数据转入极其缓慢的系统内存，最终卡死。

结论：在消费级 GPU 上，本地跑长上下文（>16K）和运行 8B 模型，目前是一个无法调和的矛盾。处理长文档的正确姿势，只能是 RAG 切片检索，而非无脑调大 OLLAMA_CONTEXT_LENGTH。

三、 几个盲区和反思

  1. 认准 Bearer 与 Token 的区别：Authorization: Bearer <token> 是 HTTP 头。Bearer 是方案，token 是实际凭证。抓包时只复制 token，千万别把 Bearer 前缀一起带进去。
  2. 区分本地代理 Key 与上游账号 Token：搭建的本地代理（如 deepseek-web2api-free）需要自己设置一个 API Key（在 .env 里写 API_KEY=sk-test），用来给 OpenScience 连接；这和你从浏览器抓下来的上游 Token 是完全两回事。
  3. 警惕端口占用：Ollama 默认端口是 11434，但端口被僵尸进程占用的概率极高。用 netstat -ano | findstr :11434 找 PID，用 taskkill /F /PID <PID> 强杀，或者直接换冷门端口（如 11436），比纠结快得多。
  4. 理解 Agent 架构要求：如果你想用 OpenScience、Claude Code 或类似工具，必须选择原生支持 Function Calling 的模型。纯聊天模型接入后，只能聊天，无法干活。
  5. 文件访问需显式授权：OpenScience 默认不允许 Agent 读取工作区外的文件。需要用 @路径 显式授权，否则它会无视你的本地文件。
  6. 不要过度期待版本升级：npm 全局安装的 CLI 和桌面应用是两套独立程序，升级时务必分别处理。老版本可能没有新模型，但新版本也可能下架你想要的免费模型。

四、 该付费付费吧大伙

对于真正想构建本地 AI 工作流的开发者，我的建议是：

  • 使用官方 API，或者本地运行原生支持工具调用的模型，能用官方 API 就用官方 API ，官方最有保障。
  • 接受合理的成本——免费往往意味着功能阉割或隐私让步，该省省该花花吧。
  • 理解“思考”与“执行”的分离架构，别指望一个纯聊天模型能接管你的电脑，从技术使用者变成技术分析者，技术学习者，技术开发者。
